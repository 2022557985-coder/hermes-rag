## 一、用一句话讲清楚

Hermes-RAG 是一套 **“先找到正确答案，再让大模型照着答案说话”** 的本地知识库问答框架。
它把企业自己的文档（Word、PDF、PPT、Markdown、网页等）变成可检索、可问答、可评估的智能知识库，并且能跑在一台普通电脑上（4 核 CPU / 8GB 内存），不用把数据送到外部服务。

如果还是有点抽象，可以这样理解：

- 没有 RAG 的大模型，像一个“只上过公开课、没看过你们公司资料的实习生”，回答公司内部问题容易瞎编。
- 有了 RAG，模型变成一个“先翻到公司手册第几页、再把那几段原文读给你听”的助手。
- Hermes-RAG 做的是最关键的中间环节：**翻得准、翻得快、可证明翻得准**。

## 二、它解决什么问题

### 2.1 大模型的“三宗罪”

| 问题 | 表现 | 本质 |
|------|------|------|
| 幻觉 | 一本正经地给出错误事实 | 模型不知道，但会编 |
| 知识过期 | 不知道公司最新制度、产品新功能 | 训练数据有截止日期 |
| 数据隐私 | 把内部资料发给外部模型服务 | 很多企业不允许数据出境 |

RAG（Retrieval-Augmented Generation，检索增强生成）是目前最主流、最务实的解法：**先检索，后生成**。回答必须建立在检索到的原文片段上，模型不再是“凭空发挥”。

### 2.2 RAG 系统的核心难点

做一个能跑的 Demo 不难，做一个能上线的系统很难。常见坑包括：

1. **检索不到**：文档切块太粗、太碎，答案分散在多个章节，召回率低。
2. **检索不准**：相似主题互相干扰，比如问“SVM 怎么处理非线性问题”，结果把“线性回归”排到第一位。
3. **分块不合理**：短章节（比如只有 48 个字的“随机森林”定义）被分块器丢掉，问题永远答不对。
4. **无法证明效果**：没有可复现的评测集，团队只能靠“感觉还行”。
5. **索引坏了没人知道**：换了嵌入模型后向量维度变化，旧索引静默失效，检索质量悄悄下降。

Hermes-RAG 的定位就是把这些坑一个个填平，做成 **可部署、可评测、可维护** 的企业级工程。

## 四、典型应用场景

### 4.1 企业内部知识库问答（最典型）

技术手册、制度文件、SOP、历史项目文档堆积如山，员工找答案靠搜索和问人。用 `python cli.py ingest /path/to/docs/` 摄入文档后，员工通过网页控制台提问，把“找文档”变成“问答案”，新人也能 30 秒定位问题。

### 4.2 客服知识库

摄入产品手册、FAQ、售后政策，启用 LLM 生成后接入客服工作台。答案带原文引用，客服敢直接照着说，减少错误承诺。

### 4.3 学术论文 / 研究报告检索

几十上百篇 PDF 需要快速定位方法、结果、结论时，调小分块粒度、提高向量检索权重，按语义检索而不是靠文件名碰运气。

### 4.4 中英文混合资料检索

跨国团队资料一半中文一半英文时，嵌入模型选 `BAAI/bge-m3`（多语言），一套配置通吃中英文问答。

### 4.5 私有化 / 数据敏感场景

政府、金融、医疗等不允许数据出网的机构，可以本地部署 + Ollama 本地大模型，全链路不出服务器。数据安全与问答能力兼得，这也是项目强调“轻量、本地化”的原因。

## 五、它到底怎么工作：一条流水线讲清楚

```
用户提问 → 查询扩展 → 并行双路检索 → RRF 融合 → 可选重排序 → 返回 Top-K / LLM 答案
```

分两个阶段理解：

**摄入阶段（建索引）**：解析后先按标题层级切大块，超过 512 token 再按语义相似度细分；每个 chunk 前缀完整标题路径。同一批 chunk 并行写入三个存储：向量库（ChromaDB）、稀疏索引（BM25）和文档存储（SQLite）。

**检索阶段（问答问题）**：粘密检索用原始问题、稀疏检索用同义词扩展后的问题；RRF 把两路 Top-100 融合成 Top-5/Top-10；需要时重排序，最后可选让 LLM 基于片段生成答案。

## 六、技术栈全景

| 层次 | 技术 | 选型理由 |
|------|------|--------------------------|
| 语言 | Python 3.10+ | AI 生态成熟，团队招聘容易 |
| 嵌入模型 | BAAI/bge-m3（1024 维，多语言） | 中英文效果好、开源可本地化 |

| 稀疏检索 | rank_bm25 + jieba/nltk | 纯 Python、支持中文分词、可持久化 |
| 融合算法 | 改进 RRF（动态权重） | 简单稳定、不依赖额外模型 |
| 重排序 | bge-reranker-v2-m3（可选） | 多语言精排，默认关闭控成本 |
| API 服务 | FastAPI + Uvicorn | 高性能、自动 Swagger 文档 |
| 可视化 | Gradio | 快速搭建可交互工作台 |
| 配置 | Pydantic + YAML | 类型安全、环境变量可覆盖 |
| 测试 | Pytest + Ruff | 1200+ 测试用例，CI 自动执行 |
| 部署 | Docker | 一键容器化，标准环境 |
| 大模型 | OpenAI / Ollama | 云端或本地按需选择 |

## 七、效果怎么样：用数据说话

评测环境：Windows 11，4 核 CPU / 16GB RAM，`BAAI/bge-m3` 嵌入模型。基准：40 条查询（easy 14 / medium 17 / hard 9），11 篇文档，62 个 chunk。

| 检索变体 | H@1 | H@3 | H@5 | 文档H@5 | MRR | NDCG@10 | 平均延迟 |
|---------|-----|-----|-----|---------|-----|---------|---------|
| 仅向量检索 | 80.0% | 95.0% | 100.0% | 100.0% | 0.8821 | 0.8995 | 391ms |
| Dense + BM25 RRF（默认） | 80.0% | 97.5% | 100.0% | 100.0% | 0.8883 | 0.9054 | 415ms |
| RRF + 启发式重排 | 80.0% | 97.5% | 100.0% | 100.0% | 0.8883 | 0.9054 | 417ms |

几个“人话”解读：

- **H@5 = 100%**：40 个问题前 5 条结果内一定能找到正确答案。
- **H@1 = 80%**：40 个问题里 32 个第一条就是答案，其余 8 个在前 5 条内。
- **文档级 100%**：每个问题都能找回正确的源文档，防止整篇文档漏召回。
- **失败查询 0**：chunk 级和文档级都没有彻底找不到的情况。

> 注意：当前基准以概念检索为主，40 条规模不算大。真实业务上线前，建议用自己的文档扩到 200+ 条查询再跑 `python run_eval.py`，以项目自身数据的结果为准。

## 八、怎么跑起来（5 分钟体验）

```bash
pip install -r requirements.txt
python cli.py ingest evaluation/data/sample_docs/
python cli.py query "什么是机器学习？" --top-k 5
python cli.py ui      # 浏览器打开 http://localhost:7860
python cli.py serve   # Swagger 文档 http://localhost:8000/docs
```

控制台四个工作区：对话、检索实验、评估看板、系统状态。

## 十、诚实的边界与下一步

### 当前边界

1. 评测集 40 条，以概念检索为主，规模有待扩充。
2. hard 查询首位命中率 66.7%，复杂推理类问题的“一次命中”还有提升空间。
3. 未内置 LLM 生成质量评估（Faithfulness / Answer Relevance），需接 RAGAS 脚本。
4. 单机架构，超大文档量或高并发场景需要横向扩展。

### 建议路线图

| 阶段 | 事项 | 目标 |
|------|------|------|
| 近期 | 评测集扩到 200+ 条，覆盖事实型/流程型/多文档对比 | 让数字更有说服力 |
| 中期 | 接入 bge-reranker 精排并做超时降级验证 | H@1 冲击 90%+ |
| 中期 | RAGAS 端到端问答质量评估 | 回答质量可量化 |
| 远期 | 在线 A/B 评估、缓存命中率与 P99 延迟监控 | 生产级可观测性 |

## 十一、小白词典

| 术语 | 人话解释 |
|------|----------|
| RAG | 检索增强生成：先查资料再回答的问答模式 |
| Chunk | 分块，把一篇文档切成适合检索的小段落 |
| Embedding | 嵌入向量：把文字变成一串数字，意思相近的数字相近 |
| 向量检索（Dense） | 按“意思相近”找资料 |
| 关键词检索（Sparse） | 按“字面匹配”找资料 |
| BM25 | 经典关键词排序算法，搜索引擎常用 |
| HNSW | 向量库的索引算法，让“找相似向量”变快 |
| RRF | 排名融合算法，把两路结果的排名合并 |
| MRR | 平均倒数排名：正确答案排得越靠前，分数越高 |
| NDCG | 排序质量指标：兼顾命中与否和位置 |
| Hit Rate@K | 前 K 条结果里是否包含正确答案的比例 |
| H@1 / H@5 | 第一条就命中 / 前五条内命中 |
| Top-K | 返回结果条数，通常 5 或 10 |
| HyDE | 先让模型写一段假设答案再检索，提高语义匹配 |
| Cross-Encoder | 精排模型：把问题和候选段落成对打分 |
| 索引 | 预先建立的数据结构，让检索不用每次扫全文 |

## 结语

Hermes-RAG 不是一个“玩具 Demo”，而是一个按企业标准打磨过的检索框架：检索效果有基准、索引坏损会自愈、测试覆盖到质量门槛、界面让业务人员也能上手。如果你正在规划企业知识库、客服问答或私有化 AI 助手，这个项目是一个很好的起点和参照实现。
