# ADR-003: 选择 ChromaDB 作为向量数据库

## 状态

已采纳

## 背景

需要选择一个向量数据库用于存储和检索稠密向量。选择标准：

1. 无独立进程（嵌入式）
2. 原生 Python 支持
3. 低内存占用
4. 支持持久化
5. 支持元数据过滤

## 决策

选择 **ChromaDB** 作为向量数据库，使用 HNSW 索引算法。

## 理由

### 1. 嵌入式架构

ChromaDB 是嵌入式数据库，不需要独立进程或 Docker 容器。与 FAISS 类似，但提供了更友好的 Python API 和内置的元数据管理。

### 2. 原生 Python

ChromaDB 是纯 Python 实现（底层使用 hnswlib），安装简单，无系统依赖。

### 3. 内存优化

HNSW 参数可调：
- `ef_construction=100`：降低索引构建时的搜索范围，减少内存
- `M=8`：减少图中每个节点的连接数，降低内存占用

### 4. 持久化

支持本地文件持久化，重启后无需重建索引。

### 5. 元数据过滤

支持在检索时按元数据过滤（如按文件名、页码、标题路径），与 RuleRetriever 配合使用。

## 对比分析

| 特性 | ChromaDB | FAISS | Qdrant | Milvus |
|------|----------|-------|--------|--------|
| 嵌入式 | 是 | 是 | 否 | 否 |
| 原生 Python | 是 | 是（非官方） | 否 | 否 |
| 持久化 | 是 | 手动 | 是 | 是 |
| 元数据过滤 | 是 | 否 | 是 | 是 |
| 内存占用 | 低 | 极低 | 中 | 高 |
| 安装复杂度 | pip install | pip install | Docker | Docker |

## 替代方案

### FAISS
- 优点：极致性能，内存占用最低
- 缺点：需要手动管理元数据，无内置持久化，API 不够友好

### Qdrant
- 优点：性能优秀，功能全面
- 缺点：需要独立进程，不适合资源受限环境

### LanceDB
- 优点：基于 Lance 列式存储，适合大规模
- 缺点：生态较新，社区支持不如 ChromaDB

## 后果

- 正面：零配置、嵌入式、Python 原生，满足 8GB RAM 环境要求
- 负面：大规模（百万级）场景下性能不如 Qdrant/Milvus
- 缓解：对于超大规模，可通过配置切换到其他向量数据库
