# Hermes-RAG 检索质量评估报告

版本：2.4.0 ｜ 生成日期：2026-08-01 ｜ 基准文件：`docs/eval_results.json`

## 摘要

本轮以“检索质量达到 8 分水平”为目标，对 Hermes-RAG 进行了系统性根因分析与修复。核心结论：**上一版 69.0% 的 Hit Rate@5 并非模型能力不足，而是三类可复现缺陷叠加的结果**，修复后默认变体（Dense + BM25 RRF）达到：

| 指标 | 上一版 2.3.0 | 本轮 2.4.0 | 变化 |
|------|-------------|-----------|------|
| Hit Rate@1 | 17.2% | 80.0% | +62.8pp |
| Hit Rate@3 | 58.6% | 97.5% | +38.9pp |
| Hit Rate@5 | 69.0% | 100.0% | +31.0pp |
| MRR | 0.3672 | 0.8883 | +0.5211 |
| NDCG@10 | 0.4234 | 0.9054 | +0.4820 |
| 失败查询（Top-5 未命中） | 9/29 | 0/40 | 清零 |
| 文档级 Hit Rate@5 | 未统计 | 100.0% | - |
| 平均延迟 | 492ms | 415ms | -77ms |

说明：评测集由 29 条增至 40 条，并全部改为“答案真实所在 chunk”的精确标注（详见下文“评测集治理”）。两版数字不完全可直接相减，因此变化列仅用于说明修复幅度。

## 评测集治理（重要）

上一版 29 条查询的 `relevant_chunk_ids` 大量锚定在每篇文档的 `*_0`（开篇介绍块），但答案实际位于后段章节，甚至个别答案块（如“随机森林”“分类问题详解开篇”）因分块缺陷根本不存在于索引中。这使检索系统“明明答对了却判错”。

本轮治理：

1. **修复分块丢失**：`min_chunk_size` 原先按字符数（`len(text)`）判断，实际语义应为 token 数，导致 50 字符以下的定义段被整段丢弃。改为 `estimate_tokens()` 后，所有章节均进入索引，基准索引从 57 个 chunk 增至 62 个。
2. **章节标题进入索引**：chunk 文本前缀完整标题路径（如 `监督学习详解 > 分类问题 - 分类问题是指...`），使仅靠标题才能定位的答案（“监督学习有哪些类型”“随机森林是如何工作的”）可被稠密、稀疏双路召回。
3. **重写答案标注**：40 条查询全部指向答案真实所在 chunk，并新增 `relevant_doc_ids`（文档级标注）。自动化测试 `tests/test_retrieval_quality.py` 校验每个标注 chunk 必须真实存在于基准索引，防止标注漂移再次出现。
4. **替换一条不可回答查询**：原“Python的GIL是什么？”在语料中无任何答案章节，替换为语料可回答的“Python为什么适合数据科学和人工智能？”。
5. **加入难负样本**：为 8 条区分度较高的查询新增 `negative_chunk_ids`（如“SVM使用什么方法处理非线性问题”的难负样本指向回归章节），用于检测系统是否会把近义主题混为正答；`tests/test_retrieval_quality.py` 同时校验负样本存在且不与正答重叠。

## 根因分析（上一版失败查询）

对上一版 9 条失败查询逐条做稠密/稀疏 Top-20 归零实验，三类根因：

1. **标注与答案错位（6 条）**：“逻辑回归/SVM/随机森林/决策树”系列标注在 `ml_classification.md_0`，但答案在 `_2~_5`；“K-means是什么算法”标注 `_0`，答案在 `_1`；“什么是过拟合”标注 `_0`，答案在 `_4`。检索其实已经召回正确答案。
2. **分块丢数据（2 条）**：`分类问题详解`开篇（49 字符）与 `随机森林`章节（48 字符）因字符数低于 50 被整段丢弃，任何检索路径都不可能命中。
3. **扩展噪声破坏稠密排序（1 条）**：“Python为什么适合数据科学和人工智能？”在查询扩展加入“样本/数据集/资料”后，正确答案从稠密第 3 跌至第 9。修复后稠密使用原始查询、稀疏使用扩展查询。

## 本轮修复清单

### 分块（Chunking）

- `min_chunk_size` 改为 token 计数：`_estimate_tokens()`，默认值 50 → 20 token
- chunk 文本前缀完整标题路径（`metadata_builder.get_heading_path()`），标题参与稠密/稀疏匹配
- 基准索引 57 → 62 chunks，无章节丢失

### 检索（Retrieval）

- 稀疏路径改用扩展查询（同义词参与 BM25），稠密路径保持原始查询，避免扩展噪声
- 新增 ML 领域同义词：过拟合/欠拟合/随机森林/决策树/逻辑回归/SVM/K-means/监督学习/无监督学习/反向传播/激活函数/ResNet/装饰器/类型/数据科学 等 30+ 组
- 多路召回保持 Dense + BM25 RRF（默认 0.8 稠密 / 0.2 稀疏，口语化查询）

### 重排（Reranking）

- 修复启发式重排器分数尺度不一致：原始 RRF 分先做 min-max 归一化再与标题/关键词分加权，权重回归 0.55 / 0.20 / 0.20 / 0.05
- 默认仍关闭重排（RRF 为最强变体），启发式作为可选项保留

### 工程可靠性

- 索引版本号（`IndexManager.INDEX_VERSION`）持久化到 DocumentStore `meta` 表；分块策略升级后启动时自动从文档存储重建向量与 BM25，避免旧索引静默失效
- 基准新增文档级指标：`doc_hit_rate@1/3/5`、`doc_mrr`、`doc_recall@5`，JSON 报告新增 `doc_failed_queries`
- 评测集质量门禁：`tests/test_retrieval_quality.py` 校验标注 chunk 存在性、标注结构、分块行为与文档级指标
- Gradio 评估看板新增“文档H@5”“失败查询”卡片与列

## 后续优化建议

1. 扩充评测集至 200+ 条并加入负样本，覆盖事实型/流程型/多文档对比型查询
2. 引入 cross-encoder（`BAAI/bge-reranker-v2-m3`）精排并做超时降级验证
3. 为 hard 查询加入多查询改写与文档级聚合检索，冲击 H@1 ≥ 90%
4. 增加 LLM 生成指标（Faithfulness / Answer Relevance）与端到端问答评测
5. 建立在线 A/B 评估，跟踪缓存命中率与 P99 延迟
